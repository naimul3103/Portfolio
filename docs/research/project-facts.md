### 5.1 `skill-tracker-api`

```yaml
title: "Skill Tracker API"
slug: "skill-tracker-api"
oneLiner: "A layered FastAPI service for tracking skills and learning journals, with cross-resource validation and a RESTRICT-style delete guard."
category: personal        # [I] no course framing anywhere; owner is sole author of both commits
stack: [Python 3.10+, FastAPI 0.146.0, Pydantic 2.14.1, Uvicorn 0.54.0, Starlette 1.9.0]
status: wip
```

- **Problem.** Learning logs and skill ratings usually live in a spreadsheet, which cannot enforce that a journal entry points at a real skill — so entries silently orphan when a skill is renamed or removed. The interesting question here is data integrity at an API boundary, not CRUD.
- **Approach.** Deliberate separation of concerns: `schemas.py` (Pydantic contracts incl. a 1–10 rating range), `db.py` (shared store so routers never import each other), `routers/skills.py` + `routers/journals.py` (thin handlers). `PUT` uses `model_dump(exclude_unset=True)` so partial updates don't null out untouched fields. Delete performs a dependency scan across `JOURNALS_DB` and returns `400` rather than orphaning rows (`routers/skills.py:107-115`). Dependency set is pinned exactly, so the environment is reproducible.
- **Outcome claims.**
  - **12 HTTP routes** (10 CRUD + `GET /` + `GET /health`) — *method: manual enumeration of route decorators in `main.py` and both routers; re-countable in a minute.* **VERIFIED.**
  - **RESTRICT guard rejects deletes with dependent journals (HTTP 400)** — *method: code path read at `routers/skills.py:107-115`.* **VERIFIED in code, not exercised by a test — no test suite exists.**
  - Test coverage: **0%** — *method: no `tests/` directory in the tree.* Stated as a fact, not a virtue.
  - `TODO: needs owner metric` — p50/p95 latency on `/skills/`; requests/sec; number of skills/journals actually tracked.
- **Evidence.** [Repo](https://github.com/naimul3103/skill-tracker-api) · [RESTRICT logic](https://github.com/naimul3103/skill-tracker-api/blob/main/routers/skills.py#L107-L115) · [mock store](https://github.com/naimul3103/skill-tracker-api/blob/main/db.py#L1-L9) · [pinned deps](https://github.com/naimul3103/skill-tracker-api/blob/main/requirements.txt) · [README](https://github.com/naimul3103/skill-tracker-api/blob/main/README.md)
- **What I would do differently.** Ship it on SQLite via SQLAlchemy so "delete is refused" survives a restart — right now the guarantee only holds inside one process lifetime, which makes the flagship feature a demo rather than a property. Add `pytest` + `TestClient` cases for the 400 and the 422 paths *before* writing the README, so the README's claims are executable. And cut "production-style" from the description: the layering is good, the deployment story is absent, and the gap between the two is exactly what a reviewer tests first.

### 5.3 `diabetes-prediction-system`

```yaml
title: "Diabetes Risk Prediction — End-to-End ML Dashboard"
slug: "diabetes-prediction-system"
oneLiner: "A leakage-safe scikit-learn pipeline that predicts diabetes risk from 8 clinical inputs, shipped as a live Gradio dashboard with report-card output."
category: university      # source is structured as graded Tasks 1-9 + 11 with marks
stack: [Python 3.13, scikit-learn, pandas, NumPy, Matplotlib, Seaborn, Gradio 6.13.0, Hugging Face Spaces]
status: live              # Space runtime.stage=RUNNING, direct URL HTTP 200, verified 2026-10-24
```

- **Problem.** Diabetes screening data is messy in a specific, dangerous way: `Glucose`, `BloodPressure`, `SkinThickness`, `Insulin` and `BMI` record biologically impossible `0` values that mean "not measured". Treated as real zeros they drag every model toward the wrong decision boundary. The secondary problem is shipping it — a notebook that only its author can run changes nothing clinically.
- **Approach.** Explicit zero→median imputation (`:94-99`), IQR Winsorization at 1.5× (`:104-115`), two clinical features engineered — `BMI_Category` (`:132`) and `Glucose_Insulin_Ratio` as an insulin-resistance proxy (`:139`). Everything is wrapped in a single `Pipeline(SimpleImputer → StandardScaler → RandomForestClassifier)` (`:192-195`) so imputation and scaling are fit **inside** each CV fold and cannot leak. Tuned with `GridSearchCV(scoring='roc_auc', cv=StratifiedKFold(5))` (`:355-359`), reported with `StratifiedKFold(10)` (`:284`), then serialised with its feature list and metrics into `best_model.pkl` and served by a Gradio app that reads them back at boot (`app.py:7-14`).
- **Outcome claims.**
  - **Test accuracy 0.7597** — *method: 20% stratified hold-out (`test_size=0.2, random_state=42, stratify=y`, `:174-175`); value read directly from the `test_accuracy` field of the committed `best_model.pkl`.* **VERIFIED (artifact-level).**
  - **Test ROC-AUC 0.8311** — *method: same hold-out, `roc_auc_score` at `:414`; read from `test_roc_auc` in the artifact.* **VERIFIED (artifact-level).**
  - **Best CV ROC-AUC 0.8446** — *method: `GridSearchCV` 5-fold mean, stored as `cv_roc_auc` (`:515`).* **VERIFIED (artifact-level).**
  - **Deployment live** — *method: HF API `runtime.stage = RUNNING`, Gradio 6.13.0, `cpu-basic`; `https://naimul3103-diabetes-prediction-system-for-women.hf.space` returns HTTP 200; Space storage 371,056 B matches the committed model.* **VERIFIED.**
  - **Top predictors: Glucose, BMI, Age** — [R] README claim; feature importances are plotted (`:386`) but the numbers aren't committed, so **treat as README-stated, not verified**.
  - `TODO: needs owner metric` — inference latency per request on `cpu-basic`; any usage/traffic figure; calibration (Brier score) since this is a risk score people would act on.
- **Evidence.** [Repo](https://github.com/naimul3103/diabetes-prediction-system) · [Live demo](https://huggingface.co/spaces/naimul3103/diabetes-prediction-system-for-women) · [training script](https://github.com/naimul3103/diabetes-prediction-system/blob/main/final_solution_pkl.py) · [CI-safe pipeline](https://github.com/naimul3103/diabetes-prediction-system/blob/main/final_solution_pkl.py#L192-L195) · [10-fold CV](https://github.com/naimul3103/diabetes-prediction-system/blob/main/final_solution_pkl.py#L281-L289) · [app entry](https://github.com/naimul3103/diabetes-prediction-system/blob/main/app.py#L7-L14)

State the Pima/female cohort limitation on the card, since the deployed title already says "for women" but nothing explains why. And strip `.gradio/certificate.pem` from the repo.

### 5.4 `cryptomaster`

```yaml
title: "CryptoMaster — Paper-Trading Simulator"
slug: "cryptomaster"
oneLiner: "A paper-trading crypto simulator with a PHP/MySQL backend and a vanilla-JS charting frontend, priced off the Binance public API — no real money, no custody."
category: university      # README: "built as a university course project by a team of 3"
stack: [PHP 8.1+, MySQL 8.0+, PDO, Apache 2.4+ (.htaccess), vanilla HTML/CSS/JS, Chart.js 4.4.0, Binance REST API]
status: archived          # not GitHub-archived; completed course project, no deployment, last push 2026-04-13
```

- **Problem.** Reading about position sizing and P&L is not the same as doing it, but letting a learner loose with real money on an exchange is a bad idea. The gap is a sandbox that behaves like a trading desk — live prices, a real balance, holdings and cost basis — with zero financial exposure.
- **Approach.** Single-page vanilla-JS frontend (Chart.js + `chartjs-chart-financial` + `luxon` for candlesticks) against one PHP action dispatcher (`api.php?action=…`, 13 actions). Market data is proxied server-side with cURL to `api.binance.com/api/v3/ticker/24hr`, filtered to `USDT` pairs, sorted by `quoteVolume`, sliced to the top 120 — so the browser never holds an exchange key. Wallet state is server-authoritative: `wallet_save` recomputes balance from the posted trade rather than trusting a client-sent total. Hardening was treated as part of the build, not an afterthought: PDO prepared statements with `EMULATE_PREPARES => false`, bcrypt cost 12, a constant-time dummy-hash compare to defeat user enumeration, `session_regenerate_id(true)` on login, `requireAdmin()` on all four admin actions, and `.htaccess` denying `.env*`/`db.php`/`README.md` with `Options -Indexes` and four security headers.
- **Outcome claims.**
  - **13 API actions** — 9 user-facing (register, login, logout, me, market, candles, wallet_get, wallet_save, wallet_topup) + 4 admin — *method: enumeration of `case '…'` labels in `application/api.php`; matches the README table.* **VERIFIED.**
  - **Top 120 USDT pairs by 24h quote volume** — *method: `str_contains(...,'USDT')` filter `:154` → `usort` by `quoteVolume` `:158` → `array_slice($filtered, 0, 120)` `:163`.* **VERIFIED.**
  - **10/10 documented security controls present in code** — *method: line-by-line read of `api.php`, `db.php`, `.htaccess`; each control cited in §3.4.* **VERIFIED in code; not penetration-tested.**
  - **Live Binance integration** — *method: `binanceFetch()` cURL at `:64-65` calling `/ticker/24hr` `:148` and `/klines` `:171`.* **VERIFIED.**
  - `TODO: needs owner metric` — concurrent-session count; query latency for `admin_users` at scale; whether the CodeQL workflow ever ran green.
- **Evidence.** [Repo](https://github.com/naimul3103/cryptomaster) · [dispatcher](https://github.com/naimul3103/cryptomaster/blob/main/application/api.php) · [120-pair slice](https://github.com/naimul3103/cryptomaster/blob/main/application/api.php#L154-L163) · [session + admin guards](https://github.com/naimul3103/cryptomaster/blob/main/application/api.php#L119-L131) · [PDO layer](https://github.com/naimul3103/cryptomaster/blob/main/application/db.php) · [Apache rules](https://github.com/naimul3103/cryptomaster/blob/main/.htaccess) · [MIT licence](https://github.com/naimul3103/cryptomaster/blob/main/LICENSE)
- **What I would do differently.** Extract the `case` ladder into real route classes — a 13-case `switch` spanning most of a 268-line file is where the next auth bug hides, and `requireAdmin()` being a *convention* rather than middleware means one forgotten call is a privilege escalation. Add CSRF tokens (the session cookie is `SameSite=Lax`, which is mitigation, not a control) and per-IP rate limiting on `login`/`register`. Make the wallet append-only with a ledger table so P&L is auditable instead of a mutated balance. And fix my own credit line in the repo — it currently reads "Contributor Three" with a Google-search placeholder URL, which is a poor thing to link from a portfolio.
